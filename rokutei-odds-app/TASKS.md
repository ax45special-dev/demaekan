## タスク1: 実際の公式HTMLでの読み取り確認 ★最重要
**背景**: パーサーは、実物の表の「文字」から作った推測のHTMLで検証している。**実際のタグの形では、未検証。**
**許可するアクセス: 下の1レース × 2ページ(3連単・2連単/2連複)だけ。** 各1回。失敗しても、手動で2〜3回まで。**ループにしない。間隔は10秒以上空ける。**
 
対象: **2026-01-02 下関(jcd=19) 8R**
- `https://www.boatrace.jp/owpc/pc/race/odds3t?rno=8&jcd=19&hd=20260102`
- `https://www.boatrace.jp/owpc/pc/race/odds2tf?rno=8&jcd=19&hd=20260102`

手順:
1. 上記を、`python-reference` の `probe` で取る: `cd python-reference && python3 -m odds_tool --config config.json probe --date 2026-01-02 --jcd 19 --rno 8`
   (User-Agent の連絡先は、利用者に聞いて設定する。`config.json` は無ければ、`config.py` の DEFAULTS が使われる。)
2. **取れた生のHTMLを、`tests/fixtures/real_odds3t_20260102_19_08.html` と `real_odds2tf_20260102_19_08.html` として保存する**(個人名等は含まれない公開ページ。保存してよい)。
3. JS版・Python版の両方で、この実HTMLが読めるテストを追加する。
4. **合格条件(既知の値。払戻金から確認済み)**:
   - 3連単 **1-3-2 = 6.8**(100円で680円)
   - 2連単 **1-3 = 3.8**(100円で380円)
   - 3連単は **120通り**、2連単は **30通り**、2連複は **15通り**。
   - 逆数の合計が、3連単・2連単・2連複とも **1.2〜1.5**(実物の例では 1.336〜1.376)。
5. **読めなかった場合**: パーサー(`parse.js` / `parse.py`)を、実HTMLに合わせて直す。検査は弱めない。どう違っていたかを報告する(特に、2着の欄が rowspan か空セルか、`欠場` の表記、`締切時オッズ` の文言の位置)。
6. `runner.js` の `fetchOnePage` は、HTML に **`締切時オッズ`** という文字があることを要求している。実HTMLに、無ければ、**要求を直す前に、利用者に報告**する(確定前のオッズを誤って保存しないための検査)。

## タスク2: 大規模な正しさの検査(払戻金との照合)
**目的**: 日常の検査(逆数の合計)では、**単独の組の桁違いを、ほとんど検出できない**(実測: 10分の1は22/120通り、10倍は0/120通り)。これを補うため、**集めたデータを、払戻金と照合**する。
**原理**: 100円あたりの払戻金は、**当たった組の締切時オッズ ×100** と(返還・同着を除き)一致する。当たった組は**レースごとに違うマス**なので、桁違いや、行・列のずれが検出できる。

**`tools/validate_against_payouts.py` は、すでにある**(合成データでの単体テスト `tools/test_validate.py` 5個が通る。桁違い・行の取り違え・返還・同着・読み取り失敗の除外を確認済み)。やること:
1. `python3 tools/test_validate.py` が通ることを確認する。
2. **実データでの動作確認**(利用者が ZIP を届けた後): `python3 tools/validate_against_payouts.py <ZIP> --results-dir results/ --fetch`。
   - 結果(払戻金)の取得元は、Boatrace Open API(GitHub上の公開ファイル。公式サイトではない)。`--fetch` は、1日1ファイル(約2MB)を、3秒の間隔で取る。
   - **2026年より前の日(`results/v3`)は、キー名の一部が未確認のため、`payouts_from_openapi` が `NotImplementedError` を投げる。** 実物を1日分見て、実装する。
3. **許容誤差 `TOL_YEN = 5.0`(円)は、暫定。** オッズは小数1桁、払戻金は10円単位なので、通常は**ぴったり一致する**はず(例: 6.8倍 → 680円)。実データで、常にぴったり一致すると分かったら、**0に締める**。
4. **合格条件**: 実データで**一致率99%以上**(返還・同着・払戻なし・読み取り失敗を除く)。不一致があれば、原因(桁違い? 行・列のずれ? 返還?)を、1件ずつ確認して報告する。**一致率が低いなら、そのデータを分析に使わない。**

## タスク3: アプリの改善(任意・優先度順)
1. **「1レースだけ確認」ボタン**: 画面から、日付・場・R を入れて1レースだけ取り、読み取り結果の要約(通り数、逆数の合計、`1-2-3` のオッズ)を表示する。保存はしない。(README の「最初の確認手順」を、画面で完結させるため。)
2. **ログをファイルに残す**: 画面のログは、アプリが落ちると消える。`logs/run.log` に追記し(最大1MB、古い方から捨てる)、画面から読めるようにする。**裏で実行**の失敗の調査に必要。
3. **書き出しを分割**: 日数が多いと ZIP が大きくなる。「10日ごとに別のZIP」にできるようにする(`buildExport` を呼ぶ側の変更)。
4. 起動時に、`work/` に前回の途中経過が残っていれば、「前回は途中で止まりました」と表示する。

各項目: 変更 + テスト(`npm test` に追加)。画面の変更は、構文確認とロジックのテストまで(見た目は実機で確認が必要、と報告)。

## タスク4: APK のビルド
**前提(利用者に確認する)**: Expo アカウントがあるか。EAS Build の無料枠の条件は、変わるので、**現在の公式の情報で確認**する(私は確認できていない)。ビルドをどこで動かすか(Claude Code のクラウド環境から `eas build` が動かせるか、`EXPO_TOKEN` を安全に渡せるか)。

手順:
1. `eas.json` の `preview` プロファイル(APK)で、`eas build -p android --profile preview`。
2. **ビルドが失敗したら、原因を調べて直す。** 想定される所:
   - `plugins/withBackgroundActions.js`(AndroidManifest への権限・サービスの追記)。サービスのクラス名 `com.asterinet.react.bgactions.RNBackgroundActionsTask` は、ライブラリのソースで**要確認**。`foregroundServiceType="dataSync"` と、`FOREGROUND_SERVICE_DATA_SYNC` 権限(Android 14+)。
   - `react-native-background-actions` の版と、New Architecture(Expo SDK 54 の既定)の互換性。**非互換なら、代替案を、利用者に提案して選んでもらう。**
   - `ic_launcher`(通知アイコン)が、Expo のビルドに存在するか。
3. ビルド後、`aapt dump permissions`(または `apkanalyzer`)で、APK の AndroidManifest に、権限とサービスが入っていることを確認する(**実機に入れる前の検査**)。
4. **合格条件**: APK ができ、マニフェストの検査に通る。**画面を消しても動くかは、実機でしか確認できない**ので、利用者に確認手順(README)を渡し、結果を聞く。
