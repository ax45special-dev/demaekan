# KNOWLEDGE.md — 確認済みの事実と、未確認の事項

「確認済み」は、実際のページ・実際のデータで確認したもの。「未確認」は、推測を含む。**推測を事実として扱わない。**

## 1. 公式サイトのオッズページ(確認済み)
- URL: `https://www.boatrace.jp/owpc/pc/race/odds3t?rno={R}&jcd={場2桁}&hd={YYYYMMDD}`(3連単)、`odds2tf`(2連単・2連複が同じページ)。他に `odds3f`(3連複)、`oddsk`(拡連複)、`oddstf`(単勝・複勝)。`jcd` はゼロ詰め2桁(例: 下関=19、戸田=02)。
- **過去の日付でも見られる**: 2017-03-17(児島1R)、2023-03-28、2025-12-28、2026-01-02 などを確認。ページには「締切時オッズは、発売票数の集計が完了した時点でのオッズを表示しています。レース開始後の返還欠場等によるオッズの変動は反映されません。」と書かれる。
- 取得はサーバー側で作られた静的HTML(JavaScript描画ではない)。

### 表の形(文字として確認。HTMLのタグの形は未確認 → TASKS.md タスク1)
- **3連単**: 6艇ぶんのブロックが横に並ぶ。1ブロック=[2着, 3着, オッズ]の3列、全18列 × 20行 = 120通り。**2着の欄は4行ごとに1回だけ書かれ、残りは空欄**(HTMLでの表現は、rowspan か空セルか未確認。パーサーは両方に対応)。ブロックの順が1着の艇番(1〜6)。
- **2連単**: 1ブロック=[2着, オッズ]の2列、全12列 × 5行 = 30通り。
- **2連複**: 同じ12列×5行の**三角形**(使わないマスは空欄)。15通り。
- **欠場の艇**があるマスは、オッズの代わりに `欠場` と書かれる(この場合も、マスの数は変わらない)。
- **検査に使う性質**: 全マスの `1/オッズ` の合計は、控除率25%前後で約1.33になる。**実物の5つの表**(3連単1、2連単2、2連複2。3ページ分): 3連単 1.336(控除率25.2%)、2連単 1.341 と 1.344(欠場あり・20通り)、2連複 1.350 と 1.376。許容範囲を 1.2〜1.5 にしている。
  - **限界(実測)**: 実物の3連単(児島1R)の120通りで、1つの組だけを読み違えた時に、この検査で検出できるかを全数調べた。
    - **10分の1に読み違える**(例 25.3→2.53)と、検出できるのは **22通りだけ**(元のオッズが約54以下の人気の組)。残り98通り(オッズ61〜1104)は検出できない。
    - **10倍に読み違える**(例 25.3→253)と、**検出できる組は0通り**。
    - つまり、**単独の組の桁違いは、ほとんど検出できない。**
  - 検出できるのは、**構造の読み違い**(重複・欠け=行・列のずれ、取り違え)と、**多数の組が同時にずれる**ような読み違い。
  - **この限界は、タスク2(払戻金との照合)で補う。** 当たった組の締切時オッズ×100は払戻金と一致するので、**当たった組(レースごとに違うマス)の桁違いも検出できる。** 日常の検査と、事後の検査の、2段構えにする。

### 既知の値(払戻金から確認済み。タスク1の合格条件)
- **2026-01-02 下関(jcd=19) 8R**: 3連単 **1-3-2 = 6.8**(払戻680円)、2連単 **1-3 = 3.8**(払戻380円)。
  (出典: Boatrace Open API の払戻金。公式のオッズページでも 6.8 を確認済み。)

## 2. サイトポリシー(確認済み)
- boatrace.jp のサイトポリシーの禁止事項に「**不正アクセス、大量の情報送受信及び大量のアクセスなど、本サイトの運営に支障を与える行為**」。違反時は予告なく利用停止、損害賠償の責任を負う。BOATCAST も同文言(運営は同じ)。「大量」の基準は書かれていない。
- 利用者は、公式に過去オッズ約1年分の取得について問い合わせ、「大丈夫」と返信が来た、と述べている。**返信の文面・条件(件数・間隔・時間帯)を、私は見ていない。**

## 3. その日のレース一覧(確認済み)
- **Boatrace Open API**(非公式・GitHub Pages上の静的ファイル。公式サイトではない)を使う。
  - 2026-01-01以降: `https://boatraceopenapi.github.io/api/v1/YYYY/YYYYMMDD.json`。`programs.stadiums[場番号].races[R番号]` が、その日開催のレース。1ファイル約2MB。
  - それ以前(2025-05-01〜): `programs/v3/YYYY/YYYYMMDD.json`。`programs[]` の `stadium_number`、`number`。
  - 統合API(v1)には、出走表・直前情報・結果・払戻金が入っている(`payouts.trifecta[].combination/amount` 等)。
- **未確認**: Open API の利用条件(再配布・商用利用)。note.com 等で、そこから作った統計を販売する場合は、確認が要る。

## 4. これまでの研究(なぜオッズが要るか)
1年分(2025-10-06〜2026-10-05、55,788レース)の、公式の出走表・直前情報・結果・払戻金で検証した(時期で分け、過去で学習→未来で評価)。
- 勝ち順の予測は、特徴量を足すごとに、**未来の期間でも一貫して良くなる**(実力が最大、展示タイム、スタート、モーター2連率の順)。確率の較正も良い(予想65%→実際66%)。
- ところが**回収率は上がらない**: 1号艇本命+2,3,4号艇BOXの固定買いは、的中率28.5%・回収率70〜73%。モデルで相手を選ぶと、的中率33〜36%になるが、回収率は72〜76%のまま。**市場が公開情報を、ほぼ織り込んでいる**。
- 払戻金の56%が、上位10%の高配当レースに集中する。
- 払戻金(当たった組だけ)から「市場の価格」を推定する方法を作った: `期待回収率(組) = P_真(組) × 払戻の期待値`、`払戻の期待値 ∝ 1/P_市場(組)`。払戻金から市場モデル(Plackett-Luce)を学習。2連単の払戻の74%、3連単の66%を再現。
  この「期待回収率」で組を選ぶと、全部買う場合(2連単50%、3連単33%)より大きく改善した(2連単85%、3連単82%)が、**100%を超える領域は見つからなかった**。推定の過信(極端な推定ほど実際は低い)がある。
- 選手同士の相性(対戦成績)は、実力差を除くと、ほぼ存在しない(相関0.02〜0.04)。モーター交換(半年〜1年。2連率が0.0に戻る)を検出でき、モーター×コース別成績は、予測を少し改善したが、回収率には出なかった。
- **決め手に欠けた理由**: 払戻金は当たった組だけで、**外れた組のオッズが無い**。推定した市場価格は、実際のオッズより粗い。→ **実際のオッズ(120通り全部)が要る。** それで「P_真 × 実際のオッズ」を直接計算して、100%を超える組があるかを検証する。
- 必要な件数の目安: 4,600レース(約30日)で、回収率の信頼区間は約±11pt。数ptの差を見るには、もっと要る。**ランダムな30日でも、「大きなズレ」(10pt以上)の有無は分かる。**
- **正直な留意**: これは「儲かる」という結論ではない。これまで、実運用の回収率は75.7%(491件)で、市場は効率的に見える。目的は、それを実際のオッズで確かめること。

## 5. アプリの設計の判断(理由つき)
- **スマホで動かす**理由: 利用者は、スマホだけで開発している。GitHub Actions ではなく、APK。
- **裏で動かす**: フォアグラウンドサービス(通知を出しながら、JSを動かし続ける)。Expo 標準の `expo-background-task` は、定期実行で時間が短く、25分続く取得に向かない。**画面OFF時の動作は、実機でしか確認できない。** 充電中は深い省電力に入りにくい。
- 状態は JSON ファイル(`state/pending.json` 等)。取れた日は `pending` から消え、`done.json` に記録。失敗が `max_attempts_per_day`(3)回続くと「取れていない日」(`gave_up`)。
- 途中経過は、レースごとに1ファイル(`work/YYYYMMDD/JJ_RR.json`)。止まっても、取れていないレースだけを再開。
- ZIP は圧縮なしの自前実装(外部ライブラリなし)。Python の zipfile と unzip で開けることを確認済み。
- ランダム選択は、種つきの乱数(同じ設定なら、同じ日)。`balance_months` で、月ごとに散らす。

## 6. 落とし穴(実際に踏んだもの)
- テストの期待値の書き間違い(実物の表と照合せずに書いた)が、何度かあった。**期待値は、実物の表(`tests/fixtures`)を見て決める。**
- 偽サーバーの「壊れたページ」が、壊れていなかったことがあった(印を付ける処理が、壊した値を上書き)。**壊した結果、本当に検出されることを確認する。**
- 読み取り失敗の連続回数を、種類をまとめて数えると、片方だけ壊れた時に止まらない。**種類ごとに数える**(修正済み)。
- 通信のタイムアウト用タイマーを止め忘れると、受け取ったデータが60秒間メモリに残る(別のアプリで実際に起きた)。このリポジトリでは、タイマーを `finally` で必ず止めている。
- 共有後にデータを削除した日を、再び書き出さないようにしてある(`data_deleted`)。
- `react-native-background-actions` の起動オプションは **`foregroundServiceType`(単数形)**。以前は `foregroundServiceTypes` と書いていて、ライブラリに無視されていた(v4.1.0 の `src/index.js` と `BackgroundTaskOptions.java` で確認。修正済み、2026-10-07)。
- 実機で、29日分の収集が途中で止まった(2026-10-07 利用者の報告。原因のログは無し)。以前は、通信エラー・503・読み取り失敗の連続・予期しないエラーのどれでも、その回の残りの日をすべて止めていた。→ 失敗した日は記録して飛ばし、待ってから次の日へ進むように変更(止まるのは 403/429・robots.txt の禁止・停止ボタン・ページ数の上限だけ)。Python版の runner は、以前の動きのまま。
- `babel.config.js` が `babel-preset-expo` を使うのに、依存に入っていなかった(npm が `expo/node_modules` の中にしか入れない)。devDependencies に追加済み。
